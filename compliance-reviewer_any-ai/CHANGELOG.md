# Changelog

All notable changes to the Compliance Reviewer are recorded here. The tool follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html); the current version is in [VERSION](VERSION). See [Versioning](compliance-reviewer/README.md#versioning) for what counts as a major, minor or patch change.

## [2.1.1] - 2026-11-24

- **Redaction check covers free-text fields.** `validate` now runs the secret and personal-data patterns over each finding's and strength's `title`, `recommendation` and free-text `standard`, and over every check `reason` (`checks.fail.*.reason`, `checks.na`), not only evidence excerpts, as the "Redaction" rule in `finding-schema.md` already required. A match blocks the subject like an excerpt match. New unit tests cover each field and a prose-only negative case.
- **Fix.** `compliance-inventory/scripts/sensitive_scan.py` had an indentation error in `allowlisted()` that stopped the module from importing (step 01's scan, `validate` redaction and the scanner tests all failed).
- **Fix.** `render` crashed with a `TypeError` when every selected subject was N/A (for example a Data Protection-only review of a target without personal data), because the overall score is `null` then. Overall and subject scores now share one formatter: `87.50/100`, or `N/A` when no check applies. The report template no longer appends `/100` itself, and the `aggregate`/`render` console lines print `N/A` instead of `None/100`. A new unit test covers the all-N/A run end to end.

## [2.1.0] - 2026-11-24

Implements [docs/ai/plan-pii-secrets-checks_2026-11-24.md](docs/ai/plan-pii-secrets-checks_2026-11-24.md) (phases 1–5) in one release. Minor version: a new subject, a new analyzer and additive inventory fields; `schemaVersion` stays 2. **Overall scores aren't directly comparable with 2.0.0 runs** on targets that hold personal data, because the new Data Protection subject adds its checks to the overall score (it is N/A, and the overall score unchanged, when no personal data is found).

- **Evidence redaction (phase 1).** `finding-schema.md` gained a "Redaction" rule: excerpts (and titles, reasons, recommendations) never contain a secret value or personal data; workers write `<redacted:kind>` and keep the key name and line numbers. `validate` runs the shared patterns over every evidence excerpt and reports a match as a problem; `aggregate` masks every string in `90-aggregate.json` and `render` masks the report, so no value reaches `docs/reports/` or `--out-file`. The rule is also in `WORKER.md` and the SEC-OP-03/05 evidence notes.
- **Scripted secret candidates (phase 2).** New `compliance-inventory/references/secret-patterns.json` (credential formats, secret-named assignments, sensitive file names, placeholders, allowlist) and `scripts/sensitive_scan.py`. Step 01 scans every text file it walks (IaC files only with `--advanced`; lock, minified and binary files skipped; byte cap per file) and writes `secretCandidates` (`{file, line, rule, confidence}`, at most 50, never the value) and `secretCandidatesTotal`. `dispatch` passes them to `review-security-operational`, whose worker reads each candidate line even outside its 12-file sample. Sensitive files (`.env`, key files, package-manager auth files) rank first in its inventory tiers, and SEC-OP-05 explicitly covers CI workflows, Dockerfile `ARG`/`ENV`, notebook outputs and package-manager auth files.
- **`gitleaks` analyzer (phase 3).** New auto-set analyzer for `--advanced` runs: `gitleaks dir <target> --redact`, directory mode only, report written to `transitions/<runId>/02-analyzer-gitleaks.raw.json`. `dispatch` merges its file/line/rule hits with `secretCandidates` (one per file and line).
- **Data Protection subject (phase 4).** New skill `review-data-protection` (step 29, `Subject: Data Protection`, checks DPR-01 … DPR-08 with sub-subjects Storage, Exposure, Sharing, Non-Production Data, Lifecycle and Governance; 46 localized elements from OWASP Cryptographic Storage / User Privacy Protection / HTML5 cheat sheets, Top 10:2025 A04, API Security Top 10:2023 API3, NIST SP 800-122, GDPR Art. 5/25/32 principle summaries, RFC 2606, Sentry and Application Insights data-collection pages, .NET data classification, Jackson and DRF). It judges engineering controls only, never legal compliance. Check IDs use `DPR-` because `DP-` already belongs to Software Quality's Design Patterns checks. The inventory gained `piiCandidates`, `piiCandidatesTotal`, `personalDataFound` and `personalDataSignals`; the subject is N/A ("no personal data found") without a worker call when `personalDataFound` is false. Ownership notes were added to Security — Operational, Web & API, Input & Injection, Identity & Access and Observability.
- **Report.** The summary's subject score table also lists N/A subjects (score `N/A`).
- **Inventory map.** Tiers can set `includeExcluded` to keep generated files (migrations) and test-excluded files (fixtures) in a tier.
- **Tests and harness (phase 5).** New unit tests for the patterns (true positives, placeholders, allowlist, binaries, Luhn and IBAN checks), redaction in `validate`/`aggregate`/`render`, `secretCandidates`/`gitleaks` merging and the `personalDataFound` rule. Seeded flaws: every test app gained a fake-but-pattern-valid AWS key in `fixtures/deploy-settings.json` and a committed `.env` (A13/A14, U13/U14, M13/M14); the APIs gained seeded customer records returned whole (A15), Sentry `SendDefaultPii` in the C# API (A16), seed data with Luhn-valid card numbers (A17) and an email in the query string (A18). `answer_key.json`, `test/README.md` and `selftest_harness.py` were updated to match.

## [2.0.0] - 2026-11-20

Implements recommendations 2, 3 and 4 of [docs/ai/improvements-review_2026-11-20.md](docs/ai/improvements-review_2026-11-20.md) to lower the AI cost of a run. Major version because the worker output schema changed (`schemaVersion` 2).

- **Compact worker output (`schemaVersion` 2).** Workers no longer write `subject`, `subSubject`, `severityIfFailed`, `standard`, `url` or `urlsFetched`. They write check results as `checks: {pass: [...], fail: {id: {findingIds, reason?}}, na: {id: reason}}`, cite standards by `element` ID (plus `page` for per-version OpenAPI links), and write compact JSON. The report script derives labels and default severities from each checklist and citations from the standards files (`scripts/standards.py`). `validate` checks that each active check appears exactly once. schemaVersion 1 files are still read; re-aggregating recorded runs gives identical results, and converting them to the new schema reproduced their scores, top risks and duplicates exactly.
- **Scripted run steps.** `compliance_report.py` gained `init` (step 00: run id, `targetGitHead`, `inputsHash`, `--out-file` check), `inventory` (step 01, deterministic, driven by the new `compliance-inventory/references/subject-file-map.json` and `scripts/inventory.py`, with `--picks` for capped subjects), `na` (N/A subject files), `dispatch` (one worker payload per batch, `--only` for retries), `step`, `resume` (hash check and `--from` supersede, batch siblings included) and `validate --mark` (records subject steps in `state.json`). The orchestrator now only runs these commands, reviews capped samples, delegates the payloads and runs analyzers; the inventory skill's prompt procedure is the no-Python fallback.
- **Review packs.** Workers read one generated file per skill (`compliance-reviewer/packs/<skill>.md`) plus one per detected language (`<skill>.<language>.md`) instead of `SKILL.md`, `checklist.md`, `sources.md` and the standards files separately. Packs omit citation columns, header pin metadata, page-key tables, retired rows and `sources.md`. They are built with `compliance_report.py packs build`; `packs check` and `labels` flag a pack that is out of date.
- **Lint.** `labels` also checks that every checklist row has a `Default severity`, that every active standards element resolves to a citation, that packs are current, and that the inventory map is valid.
- Each review skill's "Citations" step now asks for `element` only; the four skills that told workers to copy labels now say the script adds them.
- The default inventory sample can differ from the earlier model-chosen one, so per-subject findings may differ between runs before and after this release.
## [1.0.1] - 2026-11-20

- Claude Code: the worker subagent (`.claude/agents/compliance-subject-reviewer.md`) now runs on Sonnet (`model: sonnet`) instead of inheriting the session's model, which should roughly halve the cost of a run (recommendation 1 of [docs/ai/improvements-review_2026-11-20.md](docs/ai/improvements-review_2026-11-20.md)). `--model` in `run_review.py`, the testers and the API now sets only the orchestrator's model.
- Test harness: `<app>-result.json` and `<app>-result.md` record the Claude cost per model (`costByModel`), so orchestrator and worker cost can be compared.

## [1.0.0] - 2026-11-16

First versioned release. It establishes the baseline: everything the tool did on this date is 1.0.0.

- 18 review subjects under `compliance-reviewer/skills/review-*`, including MCP Server, with localized, pinned standards (no URL fetching during reviews).
- Provider-neutral orchestrator and worker with thin adapters for Claude Code, GitHub Copilot, Codex/`AGENTS.md` and paste-in chat (`PROMPT.md`).
- Resumable runs via transition files (`transitions/<runId>/`), finding and transition schemas at `schemaVersion` 1.
- Deterministic report script (`compliance_report.py validate | aggregate | render | labels`) and the maintainer-only drift checker (`check_source_drift.py`).
- Operational flags, programmatic mode and the headless runner `scripts/run_review.py`.
- comp-review-api (`api/`): a FastAPI HTTP API on port 12001 with a Swagger UI. It provides about and health endpoints, reviews of uploaded source zips, the nine validation testers as background jobs, per-request AI tool and model selection, and an `Environment` setting (`production` switches the tester endpoints off: absent from Swagger, 404 on a direct call). Covered by unit tests.
- comp-review-ui (`webui/`): an Angular web UI on port 12101. It uploads a zip, or a directory zipped in the browser, runs the testers, follows jobs, and shows the final report and test result. A runtime `config.json` sets `environment` (`production` hides the testers). Covered by unit tests.

Earlier, unversioned changes are described under "Maintenance" in [compliance-reviewer/README.md](compliance-reviewer/README.md#maintenance).
