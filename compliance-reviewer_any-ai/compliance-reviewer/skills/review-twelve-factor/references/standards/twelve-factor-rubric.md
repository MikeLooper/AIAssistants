# Compliance Reviewer Twelve-Factor Rubric — local standard

- Source: authored in this repository (no external source; see `../sources.md`). Applicability provenance: the
  12factor.net introduction scopes the methodology to software-as-a-service apps (`twelve-factor-app.md`, page `idx`).
- Version: 1.0 · Created: 2026-11-09 · Elements: 20 (no website, no cap)
- Source name for `Finding.standard`: `Compliance Reviewer Twelve-Factor Rubric`
- Citation base (relative to `docs/reports/`):
  `../../compliance-reviewer/skills/review-twelve-factor/references/standards/twelve-factor-rubric.md` + `#tfr-NN`
- Level: every element is REVIEW (informational only); severity always comes from the owning check (SKILL.md).
- **Modern equivalents pass.** Anything listed under "Accepted modern equivalents" satisfies the element and the TFA
  elements of the same check. The tool names on the 12factor.net pages are examples, never requirements.
- **Fail only on a concrete fail signal** in the reviewed files, cited with file, lines and excerpt. If the comparison
  partner isn't visible, mark the check N/A ("<what> not visible"). Signals found only in development-gated
  configuration (a `Development` profile, `if DEBUG`, `docker-compose.override.yml`, a devcontainer) pass, except for
  TF-10, which compares development against production.
- An unknown framework: judge by intent where possible and add `localized-standard-gap: unknown framework <name>` to
  `notes` once.

## Applicability by deployable kind (rules, not elements)

Classify each deployable in the file list. Mark the checks excluded for its kind N/A ("not applicable to <kind>").
When a repository holds several kinds, a check applies if any deployable kind in the file list keeps it, and a
finding names the deployable that fails. If the kind can't be determined, treat the deployable as a long-running
network service, use confidence `low` on kind-dependent findings and add
`localized-standard-gap: deployable kind unclear` to `notes`.

| Deployable kind | Recognized by (examples) | Checks N/A |
|---|---|---|
| Long-running network service (web, API, gRPC, socket) | Kestrel/ASP.NET host, Spring Boot web starter, gunicorn/uvicorn/Flask/Django/FastAPI app, Express/Fastify `listen`, `EXPOSE` in Dockerfile, a Service/Ingress for it | none |
| Worker / background consumer | Generic Host `BackgroundService`, `@KafkaListener`/`@RabbitListener`, Celery/RQ worker, queue consumer entry point, no listener | TF-07 |
| Scheduled job or CLI run in a deploy | K8s `CronJob`/`Job`, cron schedule, console `Main` with args, `click`/`argparse` entry point | TF-07, TF-08 |
| Local stdio MCP server (a subprocess its MCP client launches) | MCP SDK with a stdio transport only (`WithStdioServerTransport`, `StdioServerTransportProvider`, `run()`/`run("stdio")`), no HTTP listener | TF-07, TF-08. For TF-11, `stdout` is the protocol channel, so a log event stream to `stderr` satisfies the factor; logs on `stdout` are judged by `review-mcp-server` MCP-01, not here |
| Serverless function | `host.json`/`function.json`, `serverless.yml`, SAM/`template.yaml` handlers, `@app.function_name`, Lambda handler | TF-07, TF-08, TF-09 (the platform owns process lifecycle) |
| Static front end (SPA or static site with no server of its own) | `package.json` build to `dist/`/`build/`, no server entry point | TF-04, TF-06, TF-07, TF-08, TF-09, TF-11, TF-12 |
| Library or package (no deployable entry point) | publishable package metadata (`<PackageId>`/`IsPackable`, `<packaging>jar</packaging>` without a main, `pyproject` without scripts, `package.json` `main`/`exports` only) | TF-03 … TF-12 |
| Desktop or mobile client | WinForms/WPF/MAUI/Avalonia, Android/iOS project files, Electron | TF-03 … TF-12 |

## Elements

| ID | Check | Requirement and pass criterion | Accepted modern equivalents | Fail signals (in reviewed files) |
|---|---|---|---|---|
| <a id="tfr-01"></a>TFR-01 | TF-01 | Version control is shown by `targetGitHead` ≠ `null`, or by a `.hg/`/`.svn/` directory at the root. Otherwise TFA-01 is N/A ("version control not visible: target may be an export"), never failed. Never read Git data. | Any VCS | none for TFA-01 |
| <a id="tfr-02"></a>TFR-02 | TF-01 | One codebase per app: deployables share code through project, module or package references, never through copied source. Deploys differ only in config. | Monorepo with `ProjectReference`, Maven/Gradle modules, workspace packages, internal package feed | the same source files duplicated across deployables; per-deploy code copies (`src-prod/`, `app-staging/`, `*-prod` forks); build scripts that pick different source trees per environment |
| <a id="tfr-03"></a>TFR-03 | TF-02 | Every dependency the reviewed entry points and config use is declared in the deployable's manifest. Lock files aren't judged (DEP-02). | `PackageReference`/central package management, `pom.xml`/`build.gradle`, `pyproject.toml`/`requirements*.txt`, `package.json` | no manifest for a deployable; imports of packages not declared; `<Reference HintPath>` or `sys.path`/`PYTHONPATH` pointing at machine paths; GAC or site-packages assumptions |
| <a id="tfr-04"></a>TFR-04 | TF-02 | Dependencies are isolated at run time, the same way in development and production. | Container image built from the manifest; virtualenv/Poetry/uv; per-project NuGet/Maven resolution; `node_modules` per project; self-contained publish | setup docs or scripts needing global installs for runtime deps (`npm install -g`, `sudo pip install`, `pip install` outside an image or venv); production Dockerfile installing different packages from those the manifest declares |
| <a id="tfr-05"></a>TFR-05 | TF-02 | Executables the app invokes are provided by the repo (installed with a version in the Dockerfile, declared in a manifest, or vendored). | `apt-get install <tool>=<version>` in the Dockerfile; tool as a package dependency | `Process.Start`/`subprocess`/`Runtime.exec`/`child_process` calling a tool (for example ImageMagick, `wkhtmltopdf`, `ffmpeg`, `curl`) that nothing in the repo provides |
| <a id="tfr-06"></a>TFR-06 | TF-03 | Deploy-varying values reach the app from the deploy, never from the code. *(Pass criterion.)* | Env vars; K8s ConfigMap/Secret env or file mounts; Docker/compose secrets; Key Vault, AWS Secrets Manager or Parameter Store, HashiCorp Vault, Azure App Configuration, Spring Cloud Config, located through env or platform identity; committed defaults that are local-development values only (localhost, password-less) and overridable by env | — (pass criterion) |
| <a id="tfr-07"></a>TFR-07 | TF-03 | No deploy-varying value is hardcoded. | — | hosts, URLs, connection strings, credentials, canonical hostnames, bucket or queue names, or account IDs as literals in code, or in committed config without an override path; code branching on the environment name to pick such values (`if env == "prod": url = …`); a compose or workload file with literal production values (secrets there are also SEC-OP-05, on purpose) |
| <a id="tfr-08"></a>TFR-08 | TF-03 | Environment-named config files hold no deploy-specific values. | Environment-named files with behavior settings only (log levels, feature defaults identical for every deploy of that kind) pass, with an optional `notes` remark | `appsettings.<Env>.json`, `application-<profile>.yml`, `settings/production.py` or `config/<env>.js` containing production hosts, URLs, credentials or hostnames |
| <a id="tfr-09"></a>TFR-09 | TF-04 | Every backing service is reached through a handle from config, and switching providers is a config change. | Connection strings or URLs bound from config; SDK clients built from endpoint config; provider chosen by a config value | hardcoded host, port or URL for a datastore, queue, cache, mail server or third-party API; provider implementation chosen by the environment name instead of config; a second resource's handle derived by editing the first one's string |
| <a id="tfr-10"></a>TFR-10 | TF-05 | Nothing is built, installed or changed at run time, and deploy config isn't baked into the build. | Multi-stage Dockerfile; CI builds once and promotes the same artifact; config injected at release or deploy | entrypoint or start script running `npm install`, `pip install`, `dotnet build`/`dotnet run`, `mvn package`, `git pull` or asset compilation; `npm run dev` or a development server as the production command; deploy-specific config or secrets copied or `ARG`-passed into the image |
| <a id="tfr-11"></a>TFR-11 | TF-05 | Deployments reference a unique, immutable release ID, so rollback means redeploying an earlier ID. | Image tag or digest with commit SHA, build number or version; Helm revision; platform release IDs | deployment manifests or deploy steps referencing only `:latest` or another mutable tag; a deploy step that overwrites the running artifact in place |
| <a id="tfr-12"></a>TFR-12 | TF-06 | Session and user state live in a backing store, and no routing affinity is needed. | Distributed session stores (Redis, SQL, Spring Session); stateless tokens; in-memory caches holding re-derivable data | in-memory session providers in a service deployed with more than one instance or with autoscale (`AddDistributedMemoryCache` + `AddSession`, express-session `MemoryStore`, servlet `HttpSession` without an external store, Flask filesystem sessions); session-affinity settings (ARR affinity, `sessionAffinity: ClientIP`, ingress cookie affinity) |
| <a id="tfr-13"></a>TFR-13 | TF-06 | Process-local disk is scratch only. | Uploads and generated files written to blob or object storage or a database; `emptyDir`/tmp for one request | user uploads, generated reports or job state written to a local path that later requests read; in-memory static collections or job queues treated as the source of truth |
| <a id="tfr-14"></a>TFR-14 | TF-07 | Network services host their own listener and take the port from the environment or a fixed container port. TLS may end at a platform router; never recommend a plain-HTTP public listener. | Kestrel, embedded Tomcat/Jetty/Netty (Spring Boot jar), gunicorn/uvicorn, Node `listen(process.env.PORT)`, fixed `EXPOSE` with platform port mapping | WAR or EAR deployed into an external servlet container; app only runs as a module or in-process inside an external web server (for example IIS in-process hosting with no self-host path); no listener in a service that is otherwise network-facing |
| <a id="tfr-15"></a>TFR-15 | TF-08 | Each process type runs as its own platform-managed process, scaled by count, and processes stay in the foreground. | Procfile entries, separate compose services or K8s workloads per process type, hosted worker services, replica counts or autoscalers | daemonizing (`daemon = True`, `nohup … &`, `start-stop-daemon`, `--daemon`); PID files; one container running several process types under a shell `&` or an in-container supervisor; web and worker welded into one process with no way to scale either |
| <a id="tfr-16"></a>TFR-16 | TF-09 | SIGTERM reaches the app and triggers a graceful shutdown. | Exec-form `CMD`/`ENTRYPOINT`, `exec` in wrapper scripts, `tini`/`--init`; framework graceful shutdown (Generic Host, `server.shutdown=graceful`, gunicorn/uvicorn defaults, Node `SIGTERM` handler closing the server); a termination grace period longer than the drain time | shell-form `CMD`/`ENTRYPOINT` or wrapper scripts without `exec`, so the app isn't PID 1 and gets no signal; a Node or custom server with no `SIGTERM` handling while holding connections; a grace period set shorter than the configured shutdown timeout |
| <a id="tfr-17"></a>TFR-17 | TF-09 | Startup does only what readiness needs, and it doesn't block on long one-off work. | Lazy warm-up; readiness probes; migrations as a release or one-off step (TF-12) | startup code that loads whole datasets, sleeps or retries for minutes before listening, or runs long migrations in every instance's startup path (confidence `medium` unless the cost is evident) |
| <a id="tfr-18"></a>TFR-18 | TF-10 | Development configuration uses the same type and version of each backing service as production. Judge only when both sides are visible; otherwise N/A. | `docker-compose*.yml` or devcontainer services with the same images and major versions as production IaC or manifests; emulators of the same service (for example Azurite, LocalStack) | SQLite, H2, an in-memory EF provider or LocalDB in development while production uses PostgreSQL or SQL Server; in-memory cache or queue in development while production uses Redis or RabbitMQ; the same service at a different major version in compose and production |
| <a id="tfr-19"></a>TFR-19 | TF-11 | Production logging writes to stdout/stderr. Any exporter takes its destination from the environment. | Console sinks or appenders; JSON to stdout; OTLP or collector exporter with endpoint from env (`OTEL_EXPORTER_OTLP_ENDPOINT`); file sinks only in development-gated config | file appenders or sinks, rotation settings or log paths in production config (`RollingFileAppender`, Serilog File sink, NLog file target, Python `FileHandler`/`RotatingFileHandler`, winston File transport); a hardcoded log-shipping destination in the app; logs written only to a file inside the container. Buffered stdout (for example Python without `PYTHONUNBUFFERED`) is a recommendation, not a failure. |
| <a id="tfr-20"></a>TFR-20 | TF-12 | Admin tasks are committed with the app and run from the same release, image and config as the app. | Migration tools in the repo run as a K8s `Job` or init container from the same image, `docker compose run <app> <task>`, a Procfile `release:` phase, or a CI or CD step using the built artifact | admin or migration scripts kept outside the repo or referenced by a path on a server; admin tasks needing a different runtime, dependency set or hand-installed tools; migrations applied by hand-run SQL with no runner. Migrations on every instance's startup are a TFR-17 concern and a recommendation here, not a TF-12 failure. |
